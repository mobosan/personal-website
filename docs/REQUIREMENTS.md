# Personal Website 项目需求基准

基准版本：1.0 · 整理日期：2026-10-17

来源：项目所有者提供的《任务：开发一个完整的现代化个人综合网站》，以及后续“将需求纳入项目、作为每次开发基准”的要求。本文件保留原始产品目标和约束；另行标注 V1 的具体实现选择，不把已有代码自动视为新需求。

## 1. 文档职责与使用规则

本文件定义项目应做什么、应保留哪些边界，以及如何验收。后续新增功能、修复、重构和依赖升级，均应先阅读本文件，再阅读 [架构说明](ARCHITECTURE.md) 与相关源码。

| 文件                   | 职责                                                 |
| ---------------------- | ---------------------------------------------------- |
| `docs/REQUIREMENTS.md` | 产品需求、架构约束、范围与验收标准；长期基准         |
| `docs/ARCHITECTURE.md` | 当前架构、具体设计选择、变更理由与取舍               |
| `docs/DEVELOPMENT.md`  | 启动、开发及新增文章、项目、Demo 的步骤              |
| `docs/DEPLOYMENT.md`   | Cloudflare Pages 配置与发布步骤                      |
| `docs/QA.md`           | 指定版本和环境下实际执行的验证记录；不是永久通过证明 |
| `README.md`            | 项目概览与开发入口                                   |
| 根目录 `AGENTS.md`     | 开发代理的读取顺序与执行约束                         |

使用原则：

1. 项目所有者后续明确指令可以调整本基准；记录变更，不让旧文档阻止已授权工作。
2. 未涉及的原有需求继续有效。一次局部功能请求，不意味着允许替换框架、重做全站或删除既有能力。
3. 原文中的“建议”“推荐”“可后续引入”保持其可选性质，不升级成强制约束。具体版本不永久冻结，以兼容性和实际验证为准。
4. 发现文档与实现不一致时，应指出差异并定位原因，不能仅通过放宽需求或删减测试让实现显得合规。
5. 本文件的验收清单是持续标准。是否完成，应以当前改动及对应验证证据判断，不机械沿用历史勾选或跑分。

## 2. 项目定位与范围（REQ-PRODUCT）

- 项目名称：Personal Website（暂定）；当前界面名称为 Personal Space，可集中配置。
- 定位：集个人主页、技术博客、项目作品集、在线实验室于一体的个人数字空间。
- 目标用户：个人开发者、技术爱好者及项目访问者。
- 内容方向：AI、游戏开发、Web 技术与个人项目实践。
- 主要语言：简体中文；预留未来国际化能力，不要求 V1 提供多语言翻译。
- 目标：真实、完整、可本地运行、可长期维护和扩展的网站，不是只有规划或空页面的演示。
- 开发方式：AI 辅助工程化开发；普通实现细节自主决策，不反复询问非关键问题。

### 2.1 工作目录说明

原始需求指定 `G:\web-projects\personal-website`；本次实际打开并完成开发的工作区为 `G:\web-project\personal-website`。整理时前者不存在，后者的父目录只包含本项目。

当前继续使用实际工作区。`web-project` / `web-projects` 是本机父目录命名，不是网站名称、包名或架构约束；仓库根目录名称保持 `personal-website`。不因原文单复数差异自动创建第二份项目或移动现有工作区。

如所有者以后明确要求迁移，应核对源、目标及其他目录使用者，停止占用进程，更新工作区引用与文档路径，重新验证启动和构建。项目源码、资源引用与构建逻辑应尽量使用仓库相对路径。

## 3. 技术栈与架构边界（REQ-ARCH）

| 模块       | 基准选择                                    | 约束                                        |
| ---------- | ------------------------------------------- | ------------------------------------------- |
| 框架       | Astro 稳定版                                | 默认 SSG；使用安装版本支持的官方 API        |
| 语言       | TypeScript                                  | 严格检查，不用大量 `any` 绕过问题           |
| 样式       | Tailwind CSS + CSS 变量                     | 统一主题与组件规范                          |
| 交互       | Astro 原生能力、原生 JavaScript、按需 React | 复杂交互才使用 React 岛屿，避免全站客户端化 |
| 内容管理   | Astro Content Collections                   | 集中 schema 校验与内容查询                  |
| 博客格式   | Markdown / MDX                              | 内容与展示分离                              |
| 图标       | Lucide                                      | 选用当前维护且兼容的包                      |
| 搜索       | Pagefind 可后续引入                         | V1 不强制全文索引，不为搜索引入不必要后端   |
| 包管理     | npm                                         | 提交锁文件，保持可重复安装                  |
| 版本与托管 | Git + GitHub                                | 本地版本管理与外部账号操作分开              |
| 部署       | Cloudflare Pages                            | 静态构建输出可直接部署                      |

必须保留：

- 单一、结构清晰的项目，不引入复杂 Monorepo 或微服务。
- 不引入当前需求不需要的后端服务、数据库、身份认证或全局状态框架。
- 内容页优先 Astro 静态输出，只有需要交互的部分加载脚本。
- 依赖使用稳定且彼此兼容的版本。不能仅为“最新”强行忽略 peer dependencies；不能仅为局部功能全量升级无关依赖。
- 职责明确、避免重复、类型安全、可持续扩展。优先复用现有布局、组件和数据入口，不并行搭建第二套同类系统。

### 3.1 当前实现锚点，不是永久版本锁定

V1 使用 Astro 7.4、TypeScript 6、Tailwind 4、React 19、`@lucide/astro`；具体版本由 `package.json` / `package-lock.json` 记录，Node 要求由 `engines` / `.nvmrc` 记录。

- 内容配置：`src/content.config.ts`，采用 `glob()` loader 与 `render(entry)`。
- 文章、项目：`src/content/blog/`、`src/content/projects/`。
- 查询、排序与草稿过滤：`src/lib/content.ts`。
- 站点资料、导航：`src/data/site.ts`。
- 实验注册表：`src/data/demos.ts`，区分 component / static / api。
- 主题：`src/styles/global.css`；布局：BaseLayout / ArticleLayout / ProjectLayout。

升级可以改变底层 API，但应保持产品行为、内容兼容性和以上职责边界，并在架构文档记录迁移原因。

## 4. 视觉与交互规范（REQ-UI）

### 4.1 视觉方向

70% 极简技术风 + 30% 深色科技风。参考 Linear、Vercel 的简洁感，不直接复制页面。强调现代、专业、克制、精致排版、合理留白与清晰信息层次，不能简单堆砌默认 HTML。

允许轻微蓝紫渐变、网格背景和 hover 效果，不使用大面积强烈发光或不必要的大型动画依赖。新增页面应沿用现有视觉语言；局部功能开发不默认授权全站改版。

### 4.2 主题与字体

- 实现深色、浅色双主题与手动切换，并保存用户选择。
- 原需求允许默认深色或首次跟随系统；当前选择默认深色。后续扩展不得破坏手动选择的持久化。
- 全局主题使用 CSS 变量，不把主题颜色散落硬编码到各个组件。
- 英文使用 Inter 或兼容无衬线字体，中文使用 Noto Sans SC 或系统字体，代码使用 JetBrains Mono 或兼容等宽字体。
- 不强制下载大体积完整中文字体包。

原始推荐色板仅为设计参考，具体值由现有主题变量维护，不要求每次开发恢复这些字面值：

| 角色            | 深色参考              | 浅色参考               |
| --------------- | --------------------- | ---------------------- |
| 背景            | `#0B1020`             | `#F8FAFC`              |
| 次级背景 / 卡片 | `#111827`             | `#FFFFFF`              |
| 主要文字        | `#E5E7EB`             | `#111827`              |
| 次级文字        | `#94A3B8`             | `#64748B`              |
| 强调 / 辅助强调 | `#38BDF8` / `#8B5CF6` | 沿主题调整并保证可读性 |

### 4.3 组件与动效

统一维护 Button、Card、Badge、Tag、Navbar、Footer、ThemeToggle、SectionHeading、ProjectCard、ArticleCard、DemoCard。

建议卡片圆角 12–16px、按钮圆角 8–12px、8px 基础间距、150–250ms 过渡、低对比细边框与克制阴影。参数是规范方向，按实际可读性与触控体验合理调整。

必须尊重 `prefers-reduced-motion`。持续动画提供可理解的控制，不对减少动画用户强制播放；交互需要键盘可操作与可见焦点。

## 5. 路由与功能需求

路由保持以下信息结构；可使用 Astro 的尾斜杠与动态路由文件约定：

```text
/
/blog/
/blog/[slug]/
/projects/
/projects/[slug]/
/lab/
/lab/[slug]/
/about/
/changelog/
/404（错误页；静态部署生成 404.html）
```

新增路由可以扩展此结构。已有公开 URL 的删除、改名或语义变化应有明确需求与兼容处理，避免破坏文章链接、订阅和索引。不存在的地址应显示错误页并返回正确的 404 状态。

### 5.1 首页（REQ-HOME）

包含顶部导航、Hero、精选项目、最新文章、实验室推荐、当前关注技术、页脚。Hero 有清晰视觉焦点，并适配移动端。

参考标题“探索技术，构建有趣的东西。”，副标题“记录 AI、游戏开发、Web 技术与个人项目实践。”，提供“浏览项目”“阅读文章”入口。文案可按真实个人定位调整。

### 5.2 博客（REQ-BLOG）

必须支持列表、详情、Markdown/MDX 渲染、代码高亮、标签、按日期排序、文章目录、阅读时长、上一篇/下一篇。草稿不能进入正式网站的列表、页面、RSS 或 Sitemap。

基础数据契约：

```ts
interface BlogPost {
  title: string;
  description: string;
  pubDate: Date;
  updatedDate?: Date;
  tags: string[];
  cover?: string;
  draft: boolean;
}
```

通过 Content Collections schema 实现；允许增加有实际用途的字段，例如当前的 `example`。初始化至少提供 3 篇明确标注的示例文章用于验收，不虚构作者经历或成果。以后可替换成真实内容，不要求永久保留示例文章。

当前额外提供标签筛选及标题/摘要搜索，应在未明确要求移除时保持。Pagefind 全文搜索是后续选项，不把现有简单搜索描述成全文索引。

### 5.3 作品集（REQ-PROJECTS）

提供项目列表和详情，支持封面、说明、分类、状态、技术标签、截图图集、GitHub 地址、在线体验地址与首页推荐标记。

- 类别：AI、游戏开发、Web、开发工具、其他。
- 状态：构思中、开发中、已完成、暂停维护。
- 数据集中管理，页面不散落手写项目卡片数据。
- 初始化提供若干明确标注的示例项目。概念插画不能冒充运行截图，计划技术栈不能冒充已接入能力。
- 未提供真实仓库或体验地址时，显示未配置/暂无入口，不生成伪造链接。

### 5.4 在线实验室（REQ-LAB）

作品集负责介绍项目，实验室负责直接体验。实验室包含列表、分类、详情、运行状态、可运行交互与独立体验入口。

| 类型             | 要求                               | V1 边界                                                    |
| ---------------- | ---------------------------------- | ---------------------------------------------------------- |
| A：站内组件      | React 或原生 JavaScript 集成 Astro | 至少一个真实可操作的轻量 Demo，不能只用静态图代替          |
| B：独立静态应用  | 支持 Three.js、Vite 或其他工具产物 | 可经独立路径、iframe 或独立部署接入；不要求预装所有框架    |
| C：后端/API 实验 | 可未来接入 AI Agent、模型服务等    | 保留扩展方式，不要求 V1 部署后端；未接入时明确显示规划状态 |

当前 A 为粒子场，B 为渐变配色工作台，C 为 AI Agent 规划页。后续添加 Demo 优先沿用注册表与现有集成边界；重型实验不应把运行时传递给普通文章页。

### 5.5 关于（REQ-ABOUT）

包含个人介绍、技术兴趣、技能展示、项目方向、联系方式与 GitHub 入口。未知姓名、身份、技能水平、经历、联系方式和社交账号使用明确、可修改的占位信息，不虚构。填写真实配置后应产生有效链接。

### 5.6 更新日志与错误体验（REQ-CHANGELOG）

使用结构化数据或 Markdown 管理版本号、发布日期与更新内容。只把已实现内容写为完成；未来计划与发布状态明确区分。

提供完整错误页及有意义的空状态。筛选无结果、实验尚未运行或未接入后端时，界面应解释状态，而不是显示空白或假成功。

## 7. 响应式、SEO 与性能

### 7.1 响应式与可访问性（REQ-ACCESS）

- 适配桌面、平板与手机，导航在手机上提供可访问菜单。
- 卡片列数随宽度变化，文章阅读宽度舒适。
- 代码块内部滚动，不撑破手机页面；不得出现无意义横向滚动。
- 按钮和交互控件有合理触控区域、语义名称与键盘操作路径。
- 图片有合适的替代文本；装饰性视觉不干扰辅助技术。
- 保持主题可读性与减少动画支持。

### 7.2 SEO（REQ-SEO）

每页独立 title、description、Open Graph、canonical；提供 Sitemap、RSS、robots.txt 和语义化 HTML。发布时使用真实域名，不能将占位域名当作生产配置。

### 7.3 性能（REQ-PERF）

减少不必要客户端 JavaScript；合理优化图片，非首屏图片延迟加载；避免重型动画依赖和布局偏移；Demo 使用合理加载策略。持续绘图或计时任务应清理资源，避免后台无意义运算。

使用 Lighthouse 实测性能、可访问性和 SEO，优化实际发现的问题。原需求没有要求固定 100 分门槛；不能把一次历史高分当作长期承诺，也不能伪造分数。

## 8. 工程质量与安全（REQ-QUALITY）

- 组件职责明确，命名清晰，避免重复逻辑；复杂逻辑按需添加解释。
- 不添加未使用依赖，不为了未来可能需求过度抽象。
- 严格类型检查，出现错误应查明并修复，不通过关闭检查或滥用 `any` 掩盖。
- 不把 API 密钥放到客户端或 public；`.env` 等敏感文件不得提交。
- 外链按目标采用恰当安全属性；不引入不必要第三方脚本。
- 不直接渲染不可信 HTML；仓库内可信 Markdown/MDX 与用户输入须区分。
- 不删除或覆盖用户已有项目和文件；先检查工作区与变更，再最小范围修改。

## 9. 部署边界（REQ-DEPLOY）

Cloudflare Pages 默认配置：

| 参数              | 值              |
| ----------------- | --------------- |
| Build command     | `npm run build` |
| Build output      | `dist`          |
| Production branch | `main`          |

先完成本地可运行、可构建版本与部署文档。没有必要授权、GitHub 权限或 Cloudflare 凭据时不得声称已上线。

未经所有者授权，不创建公开仓库、不发布网站、不操作外部账号。授权范围应依据会话中明确指令判断，已经给出的授权无需重复确认。

当前 `SITE_URL` 统一控制 canonical、RSS、Sitemap 和分享地址；默认 example.com 仅供本地占位。具体部署步骤见 [部署指南](DEPLOYMENT.md)。

## 10. 开发过程与架构变更规则（REQ-PROCESS）

### 10.1 每次开发

1. 阅读本基准、架构文档与相关源码，检查当前工作区改动。
2. 将本次需求对应到相关 REQ 编号，明确要改变的行为与验证方式；对普通小改动无需另建规划文件。
3. 优先沿现有组件、内容模型与目录扩展。保持本次需求之外的公开行为与架构边界。
4. 实际编写代码、按需安装依赖并分阶段验证，不能只交付计划或大量未经验证的代码。
5. 遇到问题先分析并修复；重大阻碍再说明原因，普通实现细节自主处理。
6. 完成必要检查后同步维护文档，汇报改动、验证、剩余限制；不虚构结果。

### 10.2 普通扩展与重大变更

新增文章、项目、同类组件、Demo、局部样式改进、兼容性修复及有必要的小版本升级，可以在既有需求授权内执行，不要求逐项确认。

以下属于重大架构或产品边界变更，不能仅凭开发代理偏好顺手实施：

- 替换 Astro、npm、Content Collections 或现有主题/布局体系。
- 将默认 SSG 改成 SSR 或全站 SPA，或迁移部署平台。
- 引入后端、数据库、登录服务、Monorepo、微服务或重型全局依赖。
- 不兼容地改变内容 schema、公开路由、核心功能或数据存储方式。
- 大范围重排目录、重做视觉系统，或整体升级跨主要版本依赖且需要迁移。

若用户已明确要求相应变化，按该授权执行并同步记录；若只是本次工作的可选方案，则先说明必要性、影响与迁移方案，由所有者决定。与该变化无关且已授权的工作继续推进。不能先修改本基准来制造授权。

### 10.3 变更记录

需求范围变化更新本文件；具体架构决策更新 ARCHITECTURE.md，说明原因、影响、兼容/迁移与验证方式；开发命令变化同步 README / DEVELOPMENT，部署变化同步 DEPLOYMENT。

普通修复无需重写需求。不得用“重构”名义删掉原有要求，不得把暂未实现项改写成不需要实现。

### 10.4 初始建设顺序

原始实施顺序为：环境检查与初始化 → 主题与布局 → 核心页面 → 实验室 → SEO/性能/错误体验/验证 → 文档交付。

这是初次建站流程，不是后续每轮重新初始化项目的指令。已有代码应增量维护。
